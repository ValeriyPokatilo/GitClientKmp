# Правила разработки

## Проверка перед заливкой кода

Перед тем как заливать код в удаленный репозиторий нужно проверить что всё собирается, нет ошибок
линта, и разумеется запустить проверить сделанную задачу и связанный функционал.

Для проверки компиляции, detekt и прочей автоматики использовать:

```shell
./fastcheck.sh
```

## Utils

В ютилс следует выносить функции, которые переиспользуются в разных модулях. Каждая функция в ютилс
должна иметь комментарий, объясняющий для чего эта функция была сделан, а при необходимости описание
как она работает
Если в функции ютилс происходит изменение, это следует отразить в комментарии

### validate для списка FormField

В `moko-fields` как оказалось список филдов валидируется некорректно - валидация останавливается на
первом невалидном поле. Из-за чего пользователь не видит сразу все невалидные поля, а открывает их
по одному. Для исправления этой проблемы сделана утилита:
`org.example.library.utils.FormFieldExtKt.validate`

Использовать ровно так же, как и с оригиналом, только импорт другой указывать (вместо моко -
проектный).

## ViewModel

Вьюмодель хранит состояние экрана в `CStateFlow<State>` где `State` - это data class/sealed
interface, содержащий всю необходимую для постоения экрана информацию.

Поля ввода следует выносить в отдельные `CMutableStateFlow` или `FormField`, а не хранить внутри
стейта экрана.

Не используем `init` для запуска какой-либо логики, если нужно сделать что-то при старте выносим в
функцию `onStart`, а её вызовет платформа после создания объекта вьюмодели.

### Получение ViewModel на Android

Для получения нужной ViewModel из android нужно использовать функцию:
`org.example.android.utils.viewmodel.GetViewModelKt.getViewModel`

У неё указан KDoc с примером и объяснением. Главное почему нужно использовать её:

1. `ViewModel` будет корректно сохранена в `ViewModelStore` и получена из него при пересоздании
   activity
2. В фабричный метод передается `Koin`, чтобы использовать готовые функции-фабрики типа
   `getDetailsViewModel(id = 1)`

Если у `ViewModel` есть `onStart`, то вызываться он должен **внутри** фабричного метода, то есть:

```kotlin
val viewModel = getViewModel {
    getSplashViewModel().apply(::onStart)
}
```

### Получение ViewModel на iOS

Со стороны iOS ViewModel мы получаем от Koin, тут в отличии от android специальные методы не нужны.

```swift
struct MyView: View {
    @ViewModelWrapper private var viewModel = Koin.shared.getSplashViewModel()
    
    // ...
}
```

А в случае наличия `onStart` важно обеспечить ровно один вызов этого метода - при создании нового
объекта, поэтому нужно использовать кложуру.

```swift
struct MyView: View {
    @ViewModelWrapper private var viewModel
    
    init() {
      _viewModel = .init(
        wrappedValue: { 
          let vm = Koin.shared.getSplashViewModel()
          vm.onStart()
          return vm 
        }()
      )
    }
    
    // ...
}
```

Аналогичный подход с `wrappedValue` нужен и когда у нас есть аргументы для передачи в VM.

## DI

Для DI мы используем Koin, однако не следует использовать koinViewModel или koin.get().
Для получения ViewModel используем написанные в модулях экстеншены, например
getOnboardingViewModel()
